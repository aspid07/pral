# Vision & Scope: live-конструктор архитектур

## Проблема
Статичные схемы (draw.io, Miro, C4) не позволяют показать поведение системы: нельзя прогнать флоу, нельзя увидеть, какие компоненты участвуют в конкретном сценарии, нельзя оценить нагрузку. Архитекторы и СА тратят время на ручное объяснение того, что схема должна показывать сама.

## Целевые пользователи
- Диапазон от новичка без технического бэкграунда до продвинутого архитектора — порог входа должен быть минимальным, глубина — не ограничена.
- Первая реальная аудитория: коллеги-архитекторы/СА внутри команды автора, после того как продукт достигнет пилотной готовности.

## Ключевые сценарии использования
1. Проектирование нового микросервиса и его встраивания в существующую систему на старте разработки.
2. Pre-sale: быстрый набросок архитектурного решения при минимуме входных данных.
3. Документирование AS-IS (roadmap v2+): интеграция с GitLab, построение схемы по коду в реальном времени.

## Дифференциатор
"Живость" модели — а не просто визуализация — и точное отражение AS-IS без ручного лазания в код.

## Модель данных (верхний уровень)
- **Проект** — неймспейс/контейнер. Содержит **Общую схему**: все блоки и связи между ними без конкретики (topology only).
- **Блок** — типизированный элемент схемы. MVP-набор: Actor, Microservice, Database, Message Broker, Cache. Список открыт для расширения — цель: полное покрытие типов интеграций, которые нужны архитектору.
- **Интеграция (связь)** — типизирована: API (sync), Async/messaging, WebSocket.
- **Сценарий** — самостоятельная сквозная сущность (не привязана к одному Проекту). Упорядоченный список вызовов блоков/методов, потенциально через несколько Проектов/схем. Нотация ближе к PlantUML sequence diagram. Поддерживает alt-ветвления (условия), в перспективе — parallel/retry/timeout. Один физический Сценарий может быть связан (не скопирован) с N проектов/других сценариев — композиция через ссылки.

## Механика "живости" (MVP)
Пользователь выбирает Сценарий → жмёт Start → задействованные в сценарии блоки подсвечиваются, остальные становятся серыми → токен (точка) визуально перемещается по флоу согласно порядку шагов и ветвлениям сценария.

## Границы MVP
**В скоупе:**
- Live-конструктор блоков (низкий порог входа как приоритет №1)
- Проект + Общая схема + Сценарии (модель данных выше)
- Визуальный запуск токена по сценарию с подсветкой участников и alt-ветвлениями, покрывающими реалистичные production-кейсы (включая parallel/retry/timeout — сложно, но без давления по срокам)

**Вне скоупа MVP (roadmap v2+):**
- AS-IS реверс-инжиниринг из кода / интеграция с GitLab
- Расчёт нагрузки по queueing theory (throughput, задержки)

## Нефункциональные требования
- **Безопасность данных — жёсткое требование.** Целевая аудитория (архитекторы, компании) может не захотеть, чтобы код/архитектура покидали периметр. SaaS — стартовая модель, но архитектура закладывается с прицелом на self-hosted/локальный запуск с самого начала (без vendor lock-in на управляемые облачные сервисы там, где это не критично).

## Критерий успеха MVP
60%+ участников процесса вовлечены в отслеживание через инструмент; инструмент дополняет существующие средства (не заменяет), но полностью закрывает потребность в живой демонстрации процесса.

## Ресурсы
Соло-разработка. Роли (fullstack dev, QA, аналитик, архитектор, DevOps) закрываются поэтапно в рамках совместной работы.

## Открытые вопросы для следующего этапа (системный анализ)
- Атрибуты сущностей (Проект, Блок, Связь, Сценарий, Шаг сценария) и их точная схема данных.
- Use case диаграмма и приоритизация функциональных требований.
- Выбор технологического стека с учётом NFR по self-hosted.
