# lowcode-platform

## Второе ревью CTO — авторизация (BOLA), Итерация A (эта итерация)

Внешний CTO прогнал второе ревью (см. `lowcode-platform-review-2.docx`,
28 августа 2026) и нашёл 2 находки уровня **ASAP/критично** — обе про Broken
Object-Level Authorization (BOLA, OWASP API Top 10 #1). Ниже — то, что
ревью само называет "Итерацией A", условием считать продукт пригодным для
показа реальным данным реального клиента.

**ASAP-1 — прямой доступ по id не проверялся вообще.** `PermissionService`
(`effectiveRoleOnProject`/`effectiveRoleOnScenario`, Stage 3 плана ролей)
был реализован и покрыт тестами, но НИ ОДИН контроллер его не вызывал —
"список только моих" (`ProjectService.list`/`ScenarioService.list`, п.1.3
предыдущего ревью) фильтровал по видимости только сами списки; прямой
`GET/PATCH/DELETE .../{id}` (id — просто UUID в URL/Location-заголовке/
логах) отдавал/менял/удалял чужие Project, Scenario, BlockInstance,
Connection, EntryPoint, ScenarioStep, ExecutionRun, версии сценария —
проверялся только факт валидного JWT, не то, что он вообще имеет отношение
к запрошенной сущности.

**Фикс**: `PermissionService.requireOnProject`/`requireOnScenario` — новые
guard-методы, единая точка принуждения (см. рекомендацию ревью, MEDIUM-6).
Бросают `EntityNotFoundException` (404), **не 403** — осознанный выбор: 403
подтвердил бы, что ресурс с таким id вообще существует ("оракул
существования", та же логика, что уже применена к email при регистрации,
см. `AuthService.register`) — 404 неотличим от "такого ресурса нет вообще".
Каждый затронутый `*Service.get/update/delete` (и list/create там, где это
применимо) теперь **обязан** принять `userId` и вызвать guard первым делом —
сигнатура физически не даёт его забыть (тот же приём, что уже применялся к
`ownerId` в `create()`). Read-операции — минимум READER; мутации — EDITOR;
удаление верхнеуровневого ресурса (Project, Scenario) — OWNER (то же, что
`api-contract.md` уже фиксировал для Scenario явно).

Затронуто: `ProjectService`/`Controller`, `SchemeService`/`Controller`,
`BlockInstanceService`/`Controller`, `ConnectionService`/`Controller`
(резолвит проект через `schemeId`, т.к. `connectionId` в URL без
`projectId`), `EntryPointService`/`Controller` (авторизация — на
**домашнем** проекте entry point, не на проекте вызывающей стороны — важно
из-за кросс-проектных вызовов, см. `ExecutionEngine`), `ScenarioService`/
`Controller`, `ScenarioStepService`/`Controller`, `RunService`/`Controller`
(start/getStatus/pause/resume/stop — все пять), `ScenarioGraphService`/
`Controller`, `VersioningService`/`Controller` (список/детали версий —
"история изменений чужого сценария целиком", как и предупреждает ревью;
сам `snapshot()`, вызываемый из мутаций, — без своей проверки: авторизация
уже случилась на уровне вызывающего сервиса).

**ASAP-2 — сами sharing-эндпоинты не проверяли право приглашающего.**
`POST /projects/{id}/members` и `POST /scenarios/{id}/share` запрещали
только выдать себе роль OWNER напрямую — но НИЧТО не проверяло, что
вызывающий вообще имеет право приглашать кого-либо в этот project/scenario.
Любой аутентифицированный пользователь мог вызвать `POST
/projects/{чужой-id}/members {"userId": <свой>, "role": "EDITOR"}` и
добавить себя в чужой проект сам — в обход даже честно исправленного
ASAP-1, потому что членство добывалось напрямую, не через доступ к уже
видимому ресурсу.

**Фикс**: `CollaboratorService.share/revoke/list` и
`ProjectMemberService.grant/revoke/list` теперь принимают `callerUserId` и
проверяют `requireOnScenario`/`requireOnProject(..., Role.EDITOR)` **первым
делом**, до какого-либо чтения/записи — тот же единый механизм, что и в
ASAP-1 (`grantOwner()` — исключение осознанно: вызывается один раз, сразу
после создания ресурса его создателем, до какого-либо стороннего членства,
без `callerUserId`/guard).

**Regression-тесты**: сам отчёт называет их условием закрытия итерации
(MEDIUM-7 — "ни один тест не имеет формы «пользователь B получает 403/404
при попытке доступа к ресурсу пользователя A»"). Новый
`integration/AuthorizationRegressionIntegrationTest` (Testcontainers,
настоящий Postgres, два реальных зарегистрированных пользователя) —
владелец создаёт Project/Scheme/Block/EntryPoint/Scenario, "нарушитель"
пытается GET/PATCH/DELETE их по id, запустить/прочитать чужой run,
пригласить себя через `/members`/`/share` — везде ожидается 404; отдельно
контрольный тест на то, что сам владелец по-прежнему может всё это делать.
Плюс unit-тесты на guard-методы `PermissionService` и на каждый
изменённый `*Service` (мок `PermissionService`, проверка порядка вызовов —
guard срабатывает ДО похода в репозиторий).

**Не в этой итерации** (следующие по фазировке самого ревью — Итерация
B/C): rate limiting на `/auth/**`, решение по открытой регистрации,
аутентификация STOMP-хендшейка (`/ws/**` всё ещё `permitAll()`),
Dependabot/сканирование зависимостей на CVE, Spring Modulith
verification-тест (зависимость есть, ничего не проверяет), Docker-хардening
(non-root user, HEALTHCHECK), доменные исключения вместо
`IllegalState`/`IllegalArgumentException`, политика паролей строже
минимальной длины, `UserStatusCache` без верхней границы размера — полный
список см. в самом отчёте ревью.



## Access/refresh токены — sliding session 7 дней (эта итерация)

Закрывает BLOCKER-п.1.6 из ревью CTO (Итерация 14, см. ниже) — раньше был
только один JWT на 24ч без возможности отзыва (`AppUser.enabled` +
`UserStatusCache` были минимальной защитой "прямо сейчас", не полным
решением). Теперь:

- **Access-токен** (JWT, `JwtService`) — короткоживущий, 15 минут
  (`app.jwt.expiration-ms`). Самодостаточный, проверяется на каждый запрос
  без похода в БД, как и раньше — короткий TTL ограничивает окно, в течение
  которого украденный токен вообще что-то даёт (отозвать JWT досрочно всё
  равно нельзя без blacklist'а).
- **Refresh-токен** (`RefreshTokenService`, новая таблица `refresh_token`,
  `V13__refresh_token.sql`) — непрозрачный случайный секрет (256 бит,
  `SecureRandom`), в БД хранится SHA-256 хеш, не сырое значение. Передаётся
  клиенту **только в httpOnly-cookie** (`Path=/api/v1/auth`,
  `SameSite=Strict`, `Secure`) — недоступен из JS даже теоретически, в
  отличие от access-токена, который фронт держит в памяти.
- **Sliding window 7 дней**: каждый успешный `POST /api/v1/auth/refresh`
  выдаёт новый access **и** новый refresh (ротация), а `expiresAt` нового
  refresh-токена пересчитывается заново от текущего момента — не от
  первого `login`. Сессия обрывается, только если продуктом не пользовались
  все 7 дней подряд.
- **Reuse-detection**: refresh-токен одноразовый (`replaced_by` — цепочка
  ротации). Если уже отозванный (использованный) токен предъявят повторно —
  вероятная кража секрета — отзывается вся цепочка токенов, порождённых от
  него дальше, а не только этот конкретный. Легитимный пользователь в этом
  случае будет вынужден перелогиниться.
- Новые эндпоинты: `POST /api/v1/auth/refresh`, `POST /api/v1/auth/logout`
  (отзывает refresh-токен и чистит cookie).
- **Frontend**: `api/auth.ts` — `refresh()`/`silentRestore()`; `App.tsx`
  теперь при монтировании тихо пробует восстановить сессию по refresh-cookie
  — старое ограничение "F5 разлогинивает" (см. Итерация 14, п.2.11) снято в
  пределах sliding-окна. `api/client.ts` — 401 от истёкшего access теперь
  сперва пробует тихий refresh + retry запроса, и только потом разлогинивает.
  `AuthDto.TokenResponse.token` переименован в `.accessToken` (второй токен
  в ответе появился, однозначное имя стало обязательным) — обновлены
  `seed.ps1`, `local-setup.md`.

**Тесты**: `RefreshTokenServiceTest` (Mockito — issue/rotate/revoke, sliding
window, reuse-detection на уровне логики) и новый
`integration/RefreshTokenFlowIntegrationTest` (Testcontainers, реальный
Postgres — полный HTTP-цикл ротации, reuse через настоящую id-цепочку,
logout; см. его javadoc про то, почему это не покрыть одними моками).

**Ещё не в этой итерации**: периодическая очистка протухших строк
`refresh_token` (таблица растёт без предела — есть индекс на `expires_at`
специально под будущую джобу); "выйти со всех устройств" (отозвать все
refresh-токены пользователя разом, не один конкретный); аутентификация
STOMP-хендшейка (`/ws/**` всё ещё `permitAll()` — отдельный, более старый
пункт бэклога, см. Итерация 14).



Скелет репозитория по итогам этапов бизнес-анализа → системного анализа →
UI/UX-прототипа → архитектуры → API-контракта (см. `vision-and-scope.md`,
`functional-requirements.md`, `architecture.md`, `api-contract.md`).

## ScenarioBuilder — автоматическая цепочка вложенных сценариев (эта итерация)

По фидбэку "очень трудно и не user friendly": предыдущая версия (кнопка
"+ Сценарий для ..." у каждого шага) была технически корректна, но требовала
N ручных созданий сценария с диалогом имени ради цепочки из N стрелок — три
клика и три подтверждения на то, что должно быть одним жестом рисования.

**Как это работает теперь**: выбираете/создаёте **один раз** стартовый
сценарий ("С чего начинается цепочка" — это по-прежнему явный шаг, сознательно
не автоматизирован, см. п. ниже про 1 старт). Дальше просто тяните стрелки
одну за другой. Если очередная стрелка идёт от entry point, у которого ещё
нет своего сценария — он создаётся **молча**, без диалога с именем, и шаг
сразу добавляется в него. `ScenarioBuilder` сам обходит получившуюся цепочку
вложенных сценариев (`refetchChain` — идёт по последнему root-level CALL
каждого сценария, пока не упрётся в лист или в уже посещённый узел) и
рисует её на канвасе как одну непрерывную линию, хотя "под капотом" это
по-прежнему N независимых объектов `Scenario`, связанных только совпадением
`entryPointId` — не FK-отношением.

**Защита от цикла расширена**: раньше проверялось только "не ведёт ли
стрелка в entry point ТЕКУЩЕГО сценария" (прямое A→A). Теперь — "не ведёт ли
стрелка в ЛЮБОЙ entry point, уже встретившийся где-либо раньше в цепочке"
(A→B→A тоже ловится на канвасе, а не только в рантайме) — `ExecutionEngine`
держит всю цепочку вызовов в одном стеке на весь run, не по сценарию.

**Известное ограничение**: обход цепочки (поиск "у этого entry point уже
есть сценарий?") смотрит только среди сценариев ТЕКУЩЕГО проекта — если
следующий хоп в другом проекте, автосоздание туда не дотянется, придётся
переключить проект в шапке и продолжить оттуда вручную.

По фидбэку "не понимаю, как вообще создать сценарий" — до этого момента в UI
не было СПОСОБА создать `ScenarioStep` вообще: `CreateScenarioModal` создаёт
только оболочку (имя + entry point), шаги добавлялись только через API.

Новый экран "Сценарии" (`canvas/ScenarioBuilder.tsx`) — блоки на канвасе
показывают свои entry point'ы как отдельные "розетки"
(`ScenarioBuilderNodes.tsx`, react-flow `Handle` на каждый entry point).
Стрелка = `POST .../steps` с `stepType: CALL`.

**Цепочка, а не веер** (правка по фидбэку — первая версия заставляла тянуть
все стрелки от узла "Старт", как только шагов становилось больше одного, это
выглядело неестественно и не читалось как последовательность). Теперь
разрешено вести стрелку только от блока, в который зашли на ПРЕДЫДУЩЕМ шаге
(зелёная рамка на канвасе подсказывает, откуда именно) — `Старт → A → B → C`,
как в sequence diagram, а не `Старт → A`, `Старт → B`, `Старт → C`.

Важно понимать: это честная ВИЗУАЛЬНАЯ проекция порядка выполнения
(`orderIndex`) на канвас, а не новая возможность домена — `ScenarioStep`
физически не хранит "источник" у root-level CALL, `ExecutionEngine` просто
идёт по шагам от корня по порядку; цепочка рисуется программно от
`orderIndex`, а не от того, откуда пользователь визуально тянул мышью.
"Ответная стрелка" (Б → А) из фидбэка — это просто следующий CALL по счёту,
не отдельная сущность "response": движок исполняет последовательность
вызовов, а не пары запрос/ответ. `ALT`/`PARALLEL`/`RETRY`/`TIMEOUT` и
вложенные шаги пока не визуализируются — для них по-прежнему нужен
`curl`/`seed.ps1`.

## Бэклог: `prefers-reduced-motion` гасит бегущий токен (не решено, план)

Замечено при подключении `tokens.css` (дизайн-агент, см.
`docs/ui-agent-brief.md`): глобальное правило
`@media (prefers-reduced-motion: reduce) { ... animation-duration: 0.01ms }`
в токенах — правильная практика доступности в общем, но у пользователя с
этой системной настройкой убьёт бегущий токен в `TokenEdge.tsx` (это через
`<animateMotion>`, не CSS-анимация, но `prefers-reduced-motion` в токенах
целится на CSS `animation-*`; conflict пока не проверен вживую — не факт,
что вообще пересекается технически, но по духу настройки — точно должен).

Правильное решение — не оставить токен без анимации, а ЗАМЕНИТЬ его на
дискретную подсветку узлов по шагам (то, что уже есть в `SchemeCanvas` как
`nodeStatuses`/`isActive`, только БЕЗ бегущей точки) при
`prefers-reduced-motion: reduce`. Это логика режима запуска, не чистая
вёрстка — решение затрагивает `SchemeCanvas.tsx`/`TokenEdge.tsx`, не только
CSS. Не сделано.



**Ручной цикл "остановить шелл → заменить папку → запустить заново"
неудобен.** Предлагаемое решение (не сделано): `spring-boot-devtools` в
зависимости + `gradlew bootRun --continuous` — Gradle сам пересобирает при
изменении `.java`-файлов, DevTools делает быстрый рестарт JVM без ручного
`Ctrl+C`/повторного запуска. Не проверено вживую (тот же класс ограничений,
что и весь backend — см. историю правок выше).

**Репозиторий на GitHub + доступ на пуши/коммиты.** Технически я (в этом
чат-интерфейсе) могу выполнять `git`/сетевые команды в своей песочнице
(`github.com`/`api.github.com` в списке разрешённых доменов) — но постоянно
хранить токен доступа в переписке или полагаться на то, что он переживёт
конец разговора, не стоит: у чата нет памяти между сессиями и нет
подходящего места держать секрет долго. Более естественный инструмент для
"дать Claude пуш-доступ в репозиторий на постоянной основе" — **Claude
Code** (работает локально на вашей машине, использует уже настроенные у вас
git-креды, не требует вставлять токен в чат). Инструкция по созданию
репозитория и первому пушу — ниже по запросу; про Claude Code — отдельно.

## Стоп/Пауза исполнения сценария (реализовано в этой итерации)

Из фидбэка: на экране "Запуск сценария" нужны кнопки **Стоп** (останавливает
весь run, дальше можно запустить заново) и **Пауза** (останавливается на
текущем шаге, можно либо продолжить с этого места, либо Стоп).

**Точка прерывания**: `ExecutionEngine.checkpoint()` — вызывается перед
КАЖДЫМ шагом на любом уровне вложенности (`executeSteps`, единая точка для
корневых шагов сценария и для рекурсии внутри CALL/ALT/PARALLEL/RETRY/TIMEOUT),
не только в начале `run()`. Стоп бросает внутренний `StopRequestedException`
(не бизнес-ошибка — ловится в `run()` отдельно, до общего
`catch (RuntimeException)`, чтобы не попасть в `RUN_ERROR`/`FAILED`).

**Пауза vs Стоп — разное состояние, решено так**: Пауза блокирует сам
виртуальный поток исполнения на `Lock`/`Condition` (`RunControl.awaitResumeOrStop`)
— вместо сериализации позиции в дереве шагов куда-либо и последующего
восстановления. Плюс: просто и корректно по построению — поток и так стоит
ровно там, где встал, `RunContext.callStack`/`currentStepId` никуда не делись
на время паузы. Минус, зафиксированный как ОСОЗНАННОЕ ограничение (не
устранено в этой итерации): пауза не переживает рестарт backend-процесса —
`RunControlRegistry` не персистентный, только в памяти. Полноценная
переживающая рестарт пауза потребовала бы сериализовать состояние обхода
дерева во внешнее хранилище — отдельная, более крупная задача. `@PreDestroy`
(`RunService.shutdownRunExecutor`) при shutdown прерывает такие
заблокированные потоки — `InterruptedException` в `awaitResumeOrStop`
трактуется как запрос остановки, иначе зависший на паузе run не дал бы
процессу завершиться за отведённые 10с.

**Новые статусы** (`ExecutionRun.Status`): `PAUSED`, `STOPPED` — RUNNING/
PAUSED меняет сам `ExecutionEngine.checkpoint()` (он точно знает момент,
когда движок реально встал/возобновился — не то же самое, что момент, когда
пользователь нажал кнопку); COMPLETED/FAILED/STOPPED по-прежнему выставляет
`RunService.finish()` по итоговому `RunOutcome` (добавлен третий вариант
`Outcome.STOPPED`, отдельно от `SUCCESS`/`FAILURE`).

**Новые WS-события**: `RUN_PAUSED { runId, stepId? }`, `RUN_RESUMED { runId }`,
`RUN_STOPPED { runId, stepId? }` — см. `api-contract.md`. `stepId` в
paused/stopped — последний РЕАЛЬНО завершённый шаг (undefined, если событие
случилось до первого шага).

**Новые эндпоинты**: `POST /runs/{runId}/pause|resume|stop` — все три `202
Accepted` (асинхронно: эффект подтверждается WS-событием, не самим ответом).
Валидация легального перехода — в `RunService` (409 `IllegalStateException`
через существующий `ApiExceptionHandler`, не новый код): pause только из
`RUNNING`, resume только из `PAUSED`, stop — из обоих. Небольшая, осознанно
не устранённая гонка между чтением статуса в `RunService` и реальной сменой
статуса из потока исполнения задокументирована в самом коде (`RunService`,
javadoc `requestPause`) — для визуализации потока (см. класс-комментарий
`ExecutionEngine`) это приемлемо, полноценная защита стоила бы блокировки
строки в БД ради состояния, которое и так самокорректируется на следующем
запросе.

**Frontend**: кнопки Пауза/Продолжить/Стоп в панели run mode
(`SchemeCanvas.tsx`), рядом с "Запустить" — показываются только пока
`runStatus` `running`/`paused`. `runStatus` расширен до `'paused'`/`'stopped'`;
подсветка блоков при паузе/остановке НЕ убирается (та же логика, что уже
была для ошибки — показывает, где именно всё встало). `api/runs.ts` —
`pauseRun`/`resumeRun`/`stopRun`; `ws/executionSocket.ts` — три новых
варианта `ExecutionEvent`. Заодно поправлен `api/client.ts`: `pause/resume/stop`
отвечают `202` с ПУСТЫМ телом (в отличие от уже существовавшего `202` у
`POST .../runs`, у которого тело есть) — раньше `request()` проверял только
`res.status === 204` перед `res.json()`, что упало бы `SyntaxError` на пустом
теле с любым другим кодом; заменено на проверку по факту наличия текста.

**Тесты**: `ExecutionEngineTest` — стоп до первого шага (синхронно, без
потоков), пауза-потом-резюм (с реальным вторым `Thread`, `Mockito.timeout()`
вместо `Thread.sleep` для ожидания `RUN_PAUSED`), стоп во время паузы.
`RunServiceTest` (новый) — легальные/нелегальные переходы статуса для всех
трёх действий, реальный (не мок) `RunControl` — проверяем фактическое
состояние объекта, не только факт вызова метода.

**Не в этой итерации**: тестовая инфраструктура на фронте (Vitest + RTL) —
по-прежнему не поднята, тот же пункт бэклога, что и раньше (ни одного
`*.test.ts` во всём фронтенде); "выйти со всех устройств"/массовая остановка

## Аутентификация и роли — Stage 1+2+3 (предыдущая итерация)

### Stage 1: логин/пароль + JWT

### Stage 2: роли на уровне Project (`ProjectMember`)

Гибридная модель прав из обсуждения ("пространство — грубо, сценарий —
точечно, эффективная роль = max из обоих") требует ролей на ОБОИХ уровнях —
`Collaborator` (Scenario) уже был, `ProjectMember` (Project) — новый в этой
итерации, структурно зеркалирует `Collaborator` (та же upsert-семантика,
та же защита OWNER от изменения/отзыва через API).

Заодно вынес общий `sharing.Role` enum (был вложен в `Collaborator`) — Stage 3
(`PermissionService`, ещё не реализован) будет сравнивать роль с обоих
уровней и брать максимум, для этого нужен один и тот же тип на обеих
сущностях. Порядок объявления констант (`READER < EDITOR < OWNER`) выбран
специально — естественный `compareTo()`/`ordinal()` сразу даёт "более
широкую" роль без отдельной таблицы приоритетов.

`ProjectDto.CreateRequest` получил новое поле `ownerId` (опциональное,
`nullable` — `Project` раньше вообще не имел понятия владельца, обязательное
поле сломало бы всех текущих вызывающих). Если передан — становится OWNER в
`project_member`.

API: `POST/GET /projects/{id}/members`, `DELETE /projects/{id}/members/{userId}`
— зеркалит уже существующие `/scenarios/{id}/collaborators`.

**Сознательно не стал** выносить общую генерик-абстракцию для
`CollaboratorService`/`ProjectMemberService`, хотя они структурно почти
идентичны — двух экземпляров одного паттерна недостаточно, чтобы окупить
косвенность генерик-кода. Если появится третий уровень ролей — стоит
пересмотреть.

### Stage 3: `PermissionService` — эффективная роль

`sharing.PermissionService.effectiveRoleOnScenario(scenarioId, userId)` =
`max(ProjectMember-роль на домашнем проекте сценария, Collaborator-роль на
самом сценарии)`. "Домашний проект" — тот, чей entry point сценарий
реализует (`Scenario.entryPointId → BlockInstance → Scheme → Project`).

Ещё не ЗАПРЕЩАЕТ ничего (это Stage 4) — сервис только вычисляет роль,
`hasAtLeastOnScenario`/`hasAtLeastOnProject` — удобные предикаты для
будущих проверок в контроллерах.

Заодно вынес `domain/service/EntryPointProjectResolver` — цепочка
"entry point → блок → схема → проект" резолвилась уже в третий раз
(свои копии есть в `ExecutionEngine.projectOf()` и
`ScenarioGraphService.Accumulator`) — третье появление паттерна стоит
выносить, в отличие от двух. Существующие два места **сознательно не
переведены** на этот класс — это уже протестированный рабочий код, а без
компилятора под рукой рефакторить его ради чистоты (не ради нового
поведения) — лишний риск.

По итогам обсуждения "как хранить учётки, если добавляем несколько ролей" —
согласован план из 4 стадий (self-managed логин/пароль, роли на двух уровнях:
Project — грубо, Scenario — точечно; эффективная роль = max из обоих
источников). Это Stage 1: `app_user` + логин/пароль + выпуск JWT.

- **`auth/`** — новый модуль: `AppUser` (первая настоящая таблица
  пользователей в проекте — раньше `scenario.owner_id`/`collaborator.user_id`
  были голыми `uuid` без единого FK), `AuthService` (`POST /auth/register`,
  `POST /auth/login`), `JwtService` (HS256, jjwt 0.11.5 — сознательно не
  последняя 0.12.x с другим API, см. комментарий в `build.gradle.kts`),
  `JwtAuthenticationFilter` (распознаёт `Authorization: Bearer` и кладёт
  userId в `SecurityContext`).
- **`SecurityConfig` всё ещё `permitAll()` на всё** — намеренно. Фильтр уже
  умеет распознавать токен (это нужно будущим стадиям), но пока ничего не
  ТРЕБУЕТ аутентификации: включать реальные ограничения раньше, чем появится
  `PermissionService` (Stage 3, ещё не сделан) для осмысленной проверки
  ролей — значит сломать уже написанный CRUD/ExecutionEngine без пользы.
  Stage 4 заменит `permitAll()` на `authenticated()` + ролевые проверки, и
  заодно уберёт `ownerId` из тела запроса `POST /scenarios` (сейчас клиент
  сам заявляет "я вот этот UUID" — тоже дыра, которую закроет тот же Stage 4).
- **Важное следствие миграции V8** (`FK ... NOT VALID`, т.к. в БД уже есть
  scenario/collaborator без реальных пользователей из прошлых итераций):
  создание нового `Scenario` теперь требует настоящего `app_user.id` в
  `ownerId` — `scripts/seed.ps1` и bash-версия в `docs/local-setup.md`
  обновлены: сначала регистрируют пользователя, потом используют его id.
- Регистрация (`POST /auth/register`) сейчас **открыта всем без проверки** —
  сознательное упрощение Stage 1, чтобы можно было end-to-end проверить
  логин. Для реального разворачивания "на компанию" встаёт отдельный вопрос:
  открытая регистрация с ограничением по домену почты, или только через
  админ-инструмент/приглашение — не решён, не Stage 1.
- **Не тронуто**: аутентификация WebSocket-соединений (`/ws/runs`, будущий

## Фидбэк со второго прогона (предыдущая итерация)

1. **Токен, бегущий по стрелке** — до сих пор была только подсветка блоков,
   без самого токена вдоль связи (это было в исходном видении продукта с

   скорости анимации.
2. Подпись у токена реализована как часть той же доработки — activeLabel в
   `TokenEdge`.
3. **Смена ветки ALT сбрасывает "стек запуска"** — раньше лог/подсветка от
   предыдущего прогона (с другой веткой) могли повиснуть на экране до
   следующего нажатия "Запустить", путая интерпретацию. Теперь смена любого
   ALT-селекта сама сбрасывает лог, подсветку блоков/рёбер и статус в `idle`
   (общий helper `resetRunState`, используется и здесь, и в `handleStart`).
4. **Номер запуска не отображался** — сам провод (backend → `RunDto` →
   `api/runs.ts` → `SchemeCanvas`) при проверке оказался правильным сверху
   донизу; со стороны фронтенда бага нет. Причина — рассинхрон сборок backend
   (та же категория проблем, что и раньше в этой сессии с Docker/IntelliJ):
   `run_number`/`RunDto` — из миграции `V7`, добавленной уже после прошлой
   пересборки backend на машине разработки. Решается чистым пересбором backend.

- **`@Lob` на `ScenarioVersion.snapshotJson`** — Hibernate 6 маппит `@Lob
  String` на Postgres-тип `oid` по умолчанию, а миграция объявляла колонку
  как `text`. `ddl-auto: validate` ловил расхождение при каждом старте.
  Убрали `@Lob`, добавили явный `columnDefinition = "text"`.
- **Backend регистрировал STOMP-эндпоинт с `.withSockJS()`, а frontend
  подключался напрямую через `stompjs`'s `brokerURL`** (сырой WebSocket, не
  SockJS-протокол) — два конца говорили на разных протоколах поверх одного
  URL. `WebSocket connection failed` при первом же клике "Запустить". Убрали
  `.withSockJS()` — SockJS существует ради fallback для браузеров без
  нативного WebSocket, тут не нужен.

По итогам первого прохода по UI — фидбэк и что из него сделано:

- **Скорость анимации проигрывания настраивается** (`canvas/playbackConfig.ts`
  + слайдер в панели запуска). Раньше события применялись к состоянию
  мгновенно по мере прихода с backend (а тот публикует их без пауз между
  шагами) — выглядело как мгновенная вспышка, а не анимация. Теперь события
  идут через очередь и применяются по одному с настраиваемой паузой
  (дефолт — 900мс/шаг).
- **Подсветка блоков убирается после успешного завершения** сценария (с той
  же паузой, чтобы последний шаг не исчезал мгновенно). При ошибке подсветка
  **остаётся** — последний активный блок показывает, где именно сломалось;
  это осознанный выбор, не баг.
- **Порядковый номер запуска** ("Запуск #N") — считается на backend
  (`execution_run.run_number`, миграция `V7`), переживает перезагрузку
  страницы в отличие от счётчика на фронте.
- **Новый тип блока `USER`** (человек, который может запускать/останавливать
  процесс) — миграция `V6`. `block_type` — открытый для расширения справочник
  (обычная таблица, не Java enum), так что добавление свелось к одному
  `INSERT`, без изменений кода.

**Отложено на следующие итерации** (по явной договорённости): редизайн
layout run-панели (действия слева, редактирование — панель справа) и иконки
для типов блоков вместо текстовых кодов.

## Ревью фронтенда (предыдущая итерация)

Тем же проходом, что и backend-ревью выше:

1. **Значимо — смена сценария во время запуска ломала состояние.** Селектор
   сценария не блокировался на `runStatus === 'running'` (в отличие от
   селектов ALT-веток) — переключение сценария посреди live-run перезаписывало
   `entryPointToBlockRef` под новый граф, пока WS-подписка на старый run
   продолжала слать в него события. Теперь селектор блокируется так же, как
   ALT-ветки.
2. **Значимо — обрыв WS не сигнализировался.** `subscribeToRun` не имел
   `onStompError`/`onWebSocketError`/`reconnectDelay` — неудачный коннект или
   разрыв посреди забега оставляли UI молча висеть в "Выполняется…" навсегда,
   без резервного пути. Добавлен `onConnectionError`-колбэк (это НЕ то же
   самое, что `RUN_ERROR` — "мы перестали видеть события" ≠ "сценарий упал"),
   `reconnectDelay` на транзиентные обрывы (без реплея пропущенной истории —
   backend её не хранит), и резервная кнопка "Проверить статус"
   (`GET /runs/{runId}`, `api/runs.ts:fetchRunStatus`) для ручного
   восстановления, если live-канал так и не ожил.
3. **`client.ts` выбрасывал код статуса вместо сообщения бэкенда.**
   `ApiExceptionHandler` формирует содержательный `{message}` — теперь
   `apiGet`/`apiPost` его читают и используют вместо голого "GET ... failed: 404".
4. **Непоследовательная обработка ошибок.** `fetchScenarios`/`fetchScenarioSteps`
   молча проглатывали ошибку (`catch(() => setScenarios([]))`), в отличие от
   `fetchScheme`/`fetchScenarioGraph`, которые её показывали. Теперь все четыре
   ведут себя одинаково — конкретно у каждого свой `*Error`-state в UI.
5. **`fitView` не переприменялся при смене сценария/проекта** — задокументированное
   поведение react-flow (fitView-проп подгоняет вьюпорт только при первом
   монтировании). Исправлено `key`-remount'ом `<ReactFlow>` на смену
   `selectedScenarioId`/`projectId`.
6. **Мелочи**: `nodesDraggable={mode !== 'run'}` — блоки в run-режиме
   визуализация, а не редактор, перетаскивание раньше визуально работало и
   откатывалось на следующем ре-рендере; `App.tsx` теперь грузит список
   проектов лениво (только при открытии editor mode, а не сразу при
   монтировании — стартовый экран "Запуск сценария" их не использует).

Что подтвердилось как уже сделанное верно и не требующее правок: dev-proxy в
`vite.config.ts` (`/api`, `/ws` → `localhost:8080`) настроен корректно;
`nodeTypes`/`ProjectGroupNode` вынесены на уровень модуля, не пересоздаются на
каждый рендер (частый источник react-flow warning'ов о "nodeTypes changed").

## Ревью и правки backend (предыдущая итерация)

Прошёлся по собственному коду ExecutionEngine/ScenarioGraphService/CRUD-слоя
как сеньор-ревьюер и закрыл всё по приоритету, от критичного к мелочам:

1. **Критично — `confirm=true` при удалении был сломан на уровне БД.**
   `scenario.entry_point_id` и `scenario_step.called_entry_point_id` не имели
   `ON DELETE`, и Postgres блокировал удаление даже с `confirm=true`, отдавая
   голый 500. Пофикшено миграцией `V4` (`CASCADE` для scenario, `SET NULL` для
   шага) + guard на `null` в `ExecutionEngine.executeCall` + общий
   `DataIntegrityViolationException` → 409 хендлер как предохранитель.
2. **Конкурентность.** Гонка `orderIndex` при параллельном создании шагов —
   закрыта unique-индексом (`V5`), конфликт отдаёт честный 409 вместо тихого
   дубля (ретрай в той же транзакции сознательно не делали — ненадёжен в
   Hibernate после failed flush). Убрали `@Transactional(readOnly=true)` с
   `ExecutionEngine.run()`/`ScenarioGraphService.build()`, чтобы не держать
   соединение из пула на весь обход дерева в фоновом потоке.
3. **Архитектура.** Вынесли дублирующийся `orderedChildren()` в общий
   `ScenarioStepTree`; добавили `default -> throw` в оба `switch` по
   `StepType` — без exhaustiveness-проверки компилятора забытый новый тип шага
   молча не выполнился бы вместо явной ошибки. Полный visitor поверх двух
   существенно разных walker'ов сознательно не стали городить.
4. **Производительность.** `BlockTypeLookupService` с `@Cacheable` вместо
   `blockTypeRepository.findAll()` на каждый запрос; мемоизация
   entry point → project в `ExecutionEngine.RunContext` (была уже в
   `ScenarioGraphService`, но не в движке).
5. **Тестовый пробел.** Добавлен `BlockAndEntryPointDeleteCascadeIntegrationTest`
   на Testcontainers — реальный Postgres, реальные Flyway-миграции, чёрным
   ящиком через REST API. Именно такой тест должен был поймать баг №1 —
   Mockito-юниты в принципе не видят constraint'ы БД. Требует Docker в
   окружении, где выполняется `./gradlew test` (тогда ещё был `mvn test` —
   см. "Итерация 14", с тех пор Maven убран).
6. **Мелочи.** `Location`-заголовок в `RunController`; `RunService.runExecutor`
   подключён к жизненному циклу Spring (`@PreDestroy` + `ExecutorService.close()`);
   PATCH-эндпоинты (`BlockInstanceDto`, `EntryPointDto`, `ScenarioDto`,
   `ScenarioStepDto`) переведены на честную partial-update семантику —
   отсутствующее поле в запросе больше не затирается в null.

## Что реализовано, а что нет

**Реализован полный CRUD** для всех сущностей модели данных:
- `Project` + `Scheme` (создаются вместе, каскадное удаление)
- `BlockInstance`, `Connection` — в рамках Общей схемы проекта
- `EntryPoint` — глобально адресуемый, с защитой от удаления, если на него
  ссылаются сценарии (свои или чужих проектов): `DELETE` без `?confirm=true`
  возвращает `409` со списком `referencingScenarios`
- `Scenario`, `ScenarioStep` — с проверкой уникальности `entryPointId` на
  сценарий, автоматическим `orderIndex` среди шагов одного уровня вложенности,
  валидацией CALL (обязателен `calledEntryPointId`) vs ALT/PARALLEL/RETRY/TIMEOUT
  (управляющие узлы, `calledEntryPointId` быть не должно), рекурсивным удалением
  поддерева шагов (в БД `parent_step_id` — self-FK без каскада)

Flyway-миграция (`V1__init.sql`) покрывает всю схему БД из ERD — приложение
должно подниматься и проходить `ddl-auto: validate`.

**Frontend**: `SchemeCanvas` грузит реальную Общую схему выбранного проекта
(`GET /projects/{id}/scheme`) и рендерит блоки/связи в react-flow, используя
хранимые в БД координаты (`x`/`y`) — без elkjs-раскладки (она нужна для
мульти-проектного холста в run mode, ещё не реализованного).

**Устарело на момент первого написания, актуализировано**: `SecurityConfig`
был permissive-заглушкой без аутентификации — с тех пор реализован Stage
1-4 (логин/JWT/роли/`authenticated()`, см. разделы выше). `Collaborator` /
`ScenarioVersion` были только моделями без бизнес-логики — с тех пор
реализован полный CRUD (Should-tier, см. раздел "Should-tier: шаринг и
версионирование").

**Реально ещё не реализовано**:
- Co-editing relay на Yjs (`/ws/schemes/{id}/collab`) — зависимости
  (`yjs`, `y-websocket`) в `package.json`, но нигде не импортируются
- Тестовая инфраструктура на фронте (см. раздел "Стоп/Пауза исполнения сценария")

## Мульти-проектный холст (реализован в этой итерации — закрывает последний Must-have по MoSCoW, UC5)

Новый derived-эндпоинт `GET /scenarios/{id}/graph` (не входит в исходный
`api-contract.md`, добавлен для этой задачи) обходит дерево `ScenarioStep`
сценария — рекурсивно, как `ExecutionEngine`, но:
- read-only, без событий и побочных эффектов;
- для `ALT` разворачивает **все** ветки, а не одну выбранную — цель здесь
  "что вообще может быть задействовано", а не путь конкретного run;
- при обнаружении цикла просто не разворачивает узел повторно (не бросает
  ошибку — это карта участников, а не исполнение).

Результат — список задействованных проектов (с их блоками) и рёбра вызовов
между блоками (в т.ч. пересекающие границы проектов). Фронтенд компонует это
через **elkjs** (`canvas/graphLayout.ts`) в compound-граф: проекты —
контейнеры-обёртки (`elk.algorithm: layered`, blocks вложены как children),
блоки — узлы внутри со позициями, которые elk уже отдаёт относительно
родителя — ровно то, что нужно react-flow при `parentNode`/`extent: 'parent'`.

В run mode это заменило загрузку схемы одного проекта: правая панель теперь
управляется выбором **сценария**, а не проекта (селектор проекта в шапке
остался только для editor mode). Живые события красят как отдельные блоки
(active/visited, как раньше), так и сам проект-контейнер при `CLUSTER_ENTERED`
(жирная рамка) — то, что раньше было доступно только текстом в логе.

**Известное ограничение**: bundle вырос примерно с 320 КБ до ~1.4 МБ
(minified) из-за elkjs — vite предупреждает при сборке. Для прод-версии стоит
вынести elkjs в отдельный chunk через динамический `import()`, сейчас не делал
ради простоты.

## Выбор ветки ALT (реализован в предыдущей итерации)

`POST /scenarios/{id}/runs` принимает необязательное тело
`{ branchSelections: { <altStepId>: <chosenChildStepId> } }`. Для ALT-узлов
без явного выбора `ExecutionEngine.executeAlt` по-прежнему берёт первую ветку
по `order_index` — обратная совместимость сохранена. На фронтенде: при выборе
сценария подгружаются его шаги (`GET /scenarios/{id}/steps`), среди них
ищутся ALT-узлы (на любом уровне вложенности — в т.ч. внутри PARALLEL/RETRY/
TIMEOUT), для каждого рисуется `<select>` с вариантами (`conditionLabel` ветки
или "Ветка N"), выбор уходит в `branchSelections` при старте run.

## Run mode (реализован в предыдущей итерации)

`SchemeCanvas` в режиме "Запуск сценария": выбор `Scenario` из списка, кнопка
"Запустить" → `POST /scenarios/{id}/runs` → сразу получаем `runId` и
подписываемся на `/topic/runs/{runId}` (`ws/executionSocket.ts`). Живые
события красят блоки на канвасе (жёлтый = `active`, зелёный = `visited`,
остальные блоки тускнеют, пока идёт прогон) и параллельно пишутся текстовым
логом в панели справа (`STEP_RETRYING`, `STEP_TIMEOUT`, `CLUSTER_ENTERED`,
итоговый статус). Сопоставление `targetEntryPointId → blockInstanceId` берётся
из нового поля `entryPoints` в ответе `GET /projects/{id}/scheme`.

## ExecutionEngine (реализован в предыдущей итерации)

Рекурсивно обходит `ScenarioStep`, публикует события в `/topic/runs/{runId}`.
Поддержаны все типы узлов: `CALL`, `ALT`, `PARALLEL`, `RETRY`, `TIMEOUT`.
Смысловые допущения (нет реального клиента вызовов — это визуализация потока,
а не исполнение бизнес-логики):

- **ALT** — без модели условий рантайма берёт первую ветку по `order_index`.
- **PARALLEL** — дети выполняются последовательно, получают общий
  `parallelGroupId` (id самого `PARALLEL`-узла), если свой не проставлен.
- **RETRY** — чистая симуляция (подтверждено заказчиком): публикует
  `STEP_RETRYING` `maxAttempts - 1` раз, затем один раз штатно выполняет
  обёрнутые шаги. Требует `maxAttempts >= 2` (новое поле `scenario_step.max_attempts`).
- **TIMEOUT** — реального замера времени нет; `timeoutMs` (новое поле
  `scenario_step.timeout_ms`) передаётся во `STEP_STARTED` как метаданные
  (например, для индикатора обратного отсчёта на фронтенде). Если исполнение
  обёрнутых шагов падает с ошибкой — публикуется `STEP_TIMEOUT`.
- **Циклы** — если Entry Point повторно встречается в текущем стеке вызовов
  (в т.ч. self-reference сценария на самого себя), run завершается `RUN_ERROR`
  вместо бесконечной рекурсии.
- **Кросс-проектные вызовы** — публикуют `CLUSTER_ENTERED` при пересечении
  границы проекта; `kind` в `STEP_STARTED` = `external` в этом случае,
  иначе `sync`/`async` по `EntryPoint.Kind` вызываемой точки.

`POST /scenarios/{id}/runs` возвращает `runId` сразу (202 Accepted) — сам
прогон идёт в фоне (виртуальный поток, Java 21), статус пишется в новую
таблицу `execution_run` (миграция `V3`) и читается через `GET /runs/{runId}`.

**Важно про формат событий**: каждая payload-запись в `ExecutionEventPublisher`
теперь несёт поле `type` как явный дискриминатор (`RUN_STARTED`, `STEP_STARTED`,
…) — без него фронтенд не смог бы различить события в одном топике по форме
JSON. Это была скрытая нестыковка в исходном скелете (`ExecutionEvent` на
фронте уже ожидал `type`, а бэкенд его не отправлял) — исправлено вместе с
реализацией движка.

## Запуск

Подробный пошаговый гайд с наполнением тестовыми данными через `curl` и
прохождением ключевых юз-кейсов (ALT/RETRY/TIMEOUT/PARALLEL, кросс-проектный
вызов, `confirm=true` при удалении) — **[`docs/local-setup.md`](docs/local-setup.md)**.

Коротко:
```bash
# backend
cd backend && ./gradlew bootRun     # или gradlew.bat bootRun на Windows

# frontend
cd frontend && npm install && npm run dev

# либо целиком через Docker Compose
docker compose up --build
```

Примечание: сборка backend требует доступа к Maven Central (Gradle тянет
оттуда те же зависимости), frontend — к npm registry. `.github/workflows/ci.yml`
теперь гоняет и то, и другое на каждый push/PR — см. "Итерация 14". До
появления CI backend ни разу не собирался в среде разработки, где писался
этот код (не было доступа к Gradle/Docker) — все правки по итогам ревью
проверялись только построчным чтением; с этого момента компилятор и тесты
на каждый коммит гоняет CI, а не только человек, тестирующий локально.
