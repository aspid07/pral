# Системный анализ: сущности, use cases, приоритизация

## Модель сущностей (итог)
- **Project** — неймспейс, содержит одну **Scheme** (Общая схема)
- **Scheme** — набор **Block Instance** (типизированы через **Block Type**: Actor, Microservice, DB, Broker, Cache, ...) и **Connection** между ними (integration_type: API/Async/WS; is_external — флаг межпроектной связи)
- **Entry Point** — метод/событие/WS-канал на конкретном Block Instance; единица, на которую можно сослаться из любого сценария, включая внешние по отношению к проекту
- **Scenario** — реализация ровно одного Entry Point (может отсутствовать — тогда Entry Point является листом дерева вызовов); состоит из **Scenario Step** (упорядоченных, с поддержкой вложенности для alt/parallel/retry — шаг ссылается на другой Entry Point, что рекурсивно разворачивает его Scenario, если она есть)
- Сценарий — самостоятельная переиспользуемая сущность (ссылка, не копия); может быть шарингован по ссылке с ролями Owner/Editor/Reader
- Версионирование — Scheme/Scenario/Entry Point хранят историю состояний (по аналогии с версионированием API-методов), а не только текущий AS-IS

## Актуальный список Use Case'ов
1. CRUD Проекта и Общей схемы (добавление/удаление/связывание блоков)
2. Определение Entry Point на блоке (метод API, событие, WS-канал), с поддержкой версий
3. Создание Сценария, привязанного к Entry Point; описание шагов (вызовы других Entry Point'ов, включая внешние проекты)
4. Ветвление в Сценарии: alt/condition (простое), parallel/retry/timeout (расширенное)
5. Запуск Сценария и наблюдение живого исполнения: единый холст со всеми участвующими проектами, визуальная группировка по проектам (подписанные контейнеры), подсветка участников, движение токена, никаких чёрных ящиков
6. Просмотр карты зависимостей между проектами (кто от кого зависит) — производное от is_external связей
7. Переиспользование Сценария между проектами (ссылка, не копия)
8. Просмотр истории версий Scheme/Scenario/Entry Point
9. Шаринг Сценария по ссылке с ролями Owner / Editor / Reader

## Приоритизация MVP (MoSCoW) — черновик для сверки

**Must (без этого MVP не работает):**
- UC1 — CRUD Проекта и Общей схемы
- UC2 — Entry Point (без версионирования на первом проходе)
- UC3 — Создание Сценария и шагов, включая межпроектные вызовы
- UC4 (базовое) — простое alt/condition ветвление
- UC4 (расширенное) — parallel/retry/timeout
- UC5 — Запуск и визуальное исполнение (единый холст, группировка по проектам, токен)
- UC7 — Переиспользование Сценария (ссылка)
- UC9 (базовое) — шаринг по ссылке с ролями Owner/Editor/Reader

**Should (важно, но может войти в MVP+1):**
- UC8 — версионирование и история
- UC6 — карта зависимостей между проектами

**Could (не блокирует пилот):**
- Diff между версиями Scheme/Scenario
- Расширенная аналитика по картe зависимостей

**Won't (этот MVP, уже в roadmap v2+):**
- AS-IS реверс-инжиниринг из кода / GitLab
- Расчёт нагрузки (queueing theory)

## Открытые вопросы для этапа архитектуры
- Технология раскладки составного (кластерного) графа для единого холста с группировкой по проектам (кандидаты: elkjs, dagre + custom clustering)
- Модель хранения версий (полные снэпшоты vs дельты)
- Механизм realtime-синхронизации при живом исполнении сценария (WebSocket/SSE к движку выполнения)
